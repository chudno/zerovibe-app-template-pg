# Самопроверка вживую

**Рядом с тобой приложение НЕ запущено, порт 8080 свободен.** То, что человек
видит в панели справа, — отдельная копия, которая обновляется только когда ты
СОХРАНЯЕШЬ код (см. skill `preview`). Поэтому проверяешь ты так: поднял своё
приложение локально → прогнал сценарий → погасил → сохранил → пригласил
человека смотреть.

**База данных — общая песочная** (подключение уже задано окружением, ничего
поднимать и настраивать не нужно): и твой локальный запуск, и копия в панели
смотрят в одну базу. Данные, которые ты насеешь, человек увидит сразу; а вот
КОД панель показывает только сохранённый.

Это дополняет `make check`: сборка и тесты не ловят «кнопка не туда ведёт»,
«форма не сохраняет», «пустой экран». Прогони реальный сценарий сам.

## Как проверять

### 0. Сборка и тесты зелёные
`make check` — если красный, сначала чини: живой запуск бессмысленен.
Помни: ошибки SQL-запросов видно только в e2e-тестах и вживую, компиляция их
НЕ ловит (skill `testing-rules`).

### 1. Поднять приложение локально
```sh
SETUP_TOKEN=preview-setup SECURE_COOKIE=false go run ./cmd/server >/tmp/app.log 2>&1 &
for i in $(seq 1 20); do curl -fsS http://localhost:8080/healthz >/dev/null 2>&1 && break; sleep 1; done
curl -fsS http://localhost:8080/healthz && echo OK
```
- `SETUP_TOKEN=preview-setup` — код настройки песочницы (шаг 2).
- `SECURE_COOKIE=false` — иначе логин по http://localhost не удержит сессию.
- Не поднялся — смотри `/tmp/app.log`, чини, повтори.

### 2. Первый администратор (если в приложении есть вход)
```sh
curl -s -X POST http://localhost:8080/setup \
  -d 'email=demo@demo.dev&password=demo12345&token=preview-setup'
```
201 → создан. 410 → админ в этой песочнице уже есть → просто используй те же
`demo@demo.dev` / `demo12345`. База общая — эти же креды работают и у человека
в панели. Демо в прод не уезжает: при ПУБЛИКАЦИИ вайбкодер заведёт своего
реального админа (skill `deploy`). Входа в приложении нет — пропусти.

### 3. Насеять немного данных
Пустые списки смотреть нечего — создай 2-3 примера POST-ами через формы или
админку. Человек увидит их в панели сразу (база общая).

### 4. Прогнать сценарий
Пройди путь, который затронула работа: создать запись → она в списке →
отредактировать → изменения на месте. Для админки — логин на `/admin/login`,
проверь CRUD. Убедись: нет пустых экранов, битых ссылок, несохранений.

**ОБЯЗАТЕЛЬНО дёрни GET КАЖДОЙ страницы, которую тронул** (`curl -s
localhost:8080/`, `/notes` и т.д.) — 200 и НОРМАЛЬНЫЙ HTML, не ошибка. Две
категории ошибок не ловятся сборкой и всплывают только тут:
- ошибки ШАБЛОНОВ (несуществующая функция вроде `{{seq}}`, битый `{{range}}`) —
  в шаблоне только встроенные функции, логика — в хендлере/pageData;
- ошибки SQL-запросов (опечатка в имени колонки или таблицы).

**И проверь главную глазами постороннего**: `curl -s localhost:8080/` БЕЗ
логина — с неё должен быть очевидный путь внутрь приложения (вход/регистрация
или редирект). Главная-тупик = человек решит, что приложения нет.

Нашёл проблему → чини код → перезапусти локальный сервер (`kill %1`, снова
шаг 1) → проверь снова.

### 5. Погасить
```sh
kill %1 2>/dev/null; pkill -f "cmd/server" 2>/dev/null; true
```
Не оставляй сервер работать — он больше не нужен.

## После проверки — показать человеку

1. Сохрани (`git add -A && git commit -m "…" && git push` — см. `conventions`).
2. Панель справа сама подтянет сохранённую версию через несколько секунд.
3. Скажи человеку простыми словами, что готово и что именно проверил
   («создание и редактирование записей работает, проверил вживую»).

## Если человек говорит «вижу старое»

Почти всегда — правки НЕ СОХРАНЕНЫ (нет push) или сборка красная (панель не
может собрать новую версию и держит прошлую). Прогони `make check`, почини,
сохрани — панель оживёт сама. Не пытайся «перезапустить» панель — управлять ею
не нужно и нечем.

Аргумент пользователя: $ARGUMENTS
