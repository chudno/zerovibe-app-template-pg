# Строгий цикл: Бриф → Мок → Код

ЛЮБАЯ просьба пользователя проходит этот цикл. Не «заметная», не «крупная» —
любая. Пропускать шаги нельзя; ниже точно сказано, когда шаг схлопывается.

## Шаг 1 — Бриф (правится на любое изменение)

Открой `docs/brief.md` и спроси себя: отражает ли он то, о чём просят?

- НЕ отражает (новая фича, изменение поведения, смена вида) → внеси дельту
  точечно (структура — skill `brief-interview`) и сразу push.
- Уже отражает (багфикс — возврат к задуманному; уточнение реализации) →
  бриф не трогается, шаг пройден.

Утверждение брифа (тул `ask_user`, варианты «Двигаемся к дизайну» /
«Поправить») нужно для КРУПНОГО: новая фича, новый экран, переработка. Для
мелкой дельты отдельный вопрос не задавай — утверждение случится на шаге 2
вместе с моком.

ВАЖНО про сами вопросы: утверждения задавай тулом `ask_user` (человек видит
карточку с вариантами — ему удобно кликнуть). Тул АСИНХРОННЫЙ: после вызова
ЗАВЕРШИ ход; ответ придёт следующим сообщением, и ты продолжишь с того же
места. Не жди ответ внутри хода и не задавай следующий вопрос, пока не
ответили на текущий.

## Шаг 2 — Мок (ЛЮБОЕ видимое изменение — сначала мок, потом утверждение)

«Видимое» = человек увидит это глазами: новый или изменённый экран, блок,
кнопка, компоновка, палитра, шрифт, состояние.

ЖЕЛЕЗНОЕ ПРАВИЛО: видимое изменение НЕ КОДИТСЯ, пока мок не утверждён.
Порядок всегда один:

1. Обнови или создай мок затронутых экранов в `design/` (формат — skill
   `design`). Правишь существующий экран — правь его мок, не рисуй новый.
2. Push НЕМЕДЛЕННО (вкладка «Дизайн» показывает только запушенное).
3. Спроси тулом `ask_user`: «Обновил дизайн — гляньте вкладку „Дизайн".
   Делаем так или поправить?» (варианты: «Делаем», «Поправить») и ЗАВЕРШИ
   ход — ответ придёт следующим сообщением.
4. Только после «Делаем» — шаг 3 (Код).

Мок НЕ трогается, когда в дизайне изменений нет:
- чистая логика/данные (поиск стал точнее, лимит изменился);
- багфикс, возвращающий уже утверждённый вид/поведение;
- правка текста/опечатки БЕЗ смены вида. Но если этот текст виден в моке —
  синхронизируй мок молча (без утверждения), чтобы он не врал.

## Шаг 3 — Код

1. Верстай СТРОГО по утверждённому моку — 1-в-1 (skill `design`, «Из мокапа
   в код»); слои и тесты — skill `new-feature`.
2. Приведи к дизайну и ГОТОВЫЕ страницы шаблона (вход/регистрация/
   восстановление/настройки) — ни одна страница не должна выглядеть «чужой»
   (skill `design`).
3. Живой прогон (skill `run`), сохранение (push).
4. ДОЖДИСЬ ГОТОВНОСТИ ПРЕВЬЮ, прежде чем отчитываться (жалоба реальных
   тестеров: «готово, глянь», а справа ещё заглушка несколько минут):
   `POST $ZV_AGENT_PREVIEW_REBUILD_URL`, затем поллинг
   `GET $ZV_AGENT_PREVIEW_STATUS_URL` до `ready` (детали — skill `preview`).
   Только после `ready` — «готово, глянь в окне справа». Если статус так и
   не стал `ready` — скажи честно: «обновляется, появится через пару минут».

## Железные правила

- НЕ начинай следующий шаг без явного ответа человека там, где утверждение
  положено («двигаемся», «делаем»).
- «Поправить» → правки в ТЕКУЩЕМ шаге, push, спроси снова.
- Человек торопит («давай сразу», «без вопросов») — уважь: пробеги цикл сам
  без утверждений, но АРТЕФАКТЫ (бриф, моки) всё равно создай/обнови и
  запушь — они всегда отражают реальность.
- Бриф и моки НИКОГДА не должны врать: закончил код — проверь соответствие.
- Утверждённый дизайн при переносе в код НЕ МЕНЯЕТСЯ (шрифты, цвета,
  размеры — всё видимое идентично моку). Упёрся в ограничение — сначала
  обнови мок и спроси, потом код.
- Публикация — только с явного согласия человека (skill `deploy`): после
  правок предложи «Опубликовать обновление?», НЕ переопубликовывай сам.
