# zerovibe — эталонный стартер Go + HTMX

Reference-приложение: веб-приложение на **Go + HTMX + PostgreSQL** с чистой
архитектурой. Это образец, по которому генерируются новые фичи. Полный
вертикальный срез: публичный лендинг на главной (`/`) + эталонная сущность
`Note` (на `/notes`, за авторизацией) проведена через все слои.

Один stateless Docker-контейнер на инстанс; данные — в PostgreSQL (своя база у
каждого приложения, подключение через env). Контейнер можно свободно гасить,
переносить и масштабировать — состояния в нём нет.

## Стэк

- **Go** (stdlib `net/http`, method-pattern роутинг 1.22+).
- **HTMX — интерфейс работает как SPA, без перезагрузок и мигания.** Сервер
  рендерит HTML-фрагменты, клиент их подменяет; навигация по ссылкам — через
  `hx-boost` на `<body>` (страница не перезагружается целиком). Без JS-сборки.
- **Чистый CSS** (`static/app.css`) — светлая минималистичная тема (shadcn-стиль),
  без UI-библиотек, единая опрятная база стилей.
  Вся статика (`app.css`, htmx) локальная в `internal/transport/web/static/`, вшита в
  бинарь через `embed` и раздаётся с `/static/` — без CDN в рантайме.
- **PostgreSQL** через драйвер `pgx/v5` (database/sql-интерфейс,
  позиционные `?`-плейсхолдеры).
- **html/template** (stdlib), шаблоны встроены через `embed`.
- **Миграции** — встроенный мигратор (`internal/platform/pg/migrations/*.sql`,
  PostgreSQL DDL, применяются при старте, учёт в `schema_migrations`). Схема живёт только здесь.
- **Аутентификация** на `golang.org/x/crypto/bcrypt` (хеширование паролей), сессии в БД
  + httpOnly-cookie.

## Архитектура (чистая, зависимости внутрь)

```
internal/
  domain/              сущности + инварианты + ошибки (только stdlib)
  usecase/             бизнес-логика + порты (интерфейсы репозиториев); зависит от domain
  repository/pgrepo/   реализация портов поверх PostgreSQL (database/sql)
  adapter/             внешние адаптеры (напр. platformmail — отправка писем через платформу)
  platform/pg/         подключение к PostgreSQL + мигратор
  transport/web/       HTTP/HTML на HTMX; зависит от usecase
cmd/server/            composition root: склейка слоёв + HTTP-сервер
```

Структуры конвертируются на стыках слоёв; `domain` не знает ни о БД, ни о HTTP.

## Ключевые паттерны (по ним генерируются фичи)

- **Работа с БД** (`repository/pgrepo`): стандартный `*sql.DB`; новая строка —
  `newID()` + `UPSERT`; выборки не по ключу — через `VIEW` вторичного индекса;
  связанные шаги — в serializable-транзакции. Полный свод — package doc
  `internal/repository/pgrepo`.
- **Срез фичи**: на сущность — `domain` (конструктор-валидатор) → `usecase`
  (порт + сервис) → `repository/pgrepo` (реализация порта) → `transport/web`
  (хендлеры + шаблоны).
- **HTMX (SPA без мигания)**: `GET`-страницы отдают полный HTML; мутации
  (`POST`/`DELETE`) возвращают ровно тот фрагмент, который меняется — htmx
  подменяет его на клиенте. Навигация по ссылкам — через `hx-boost` на `<body>`:
  переходы без полной перезагрузки, контент не пропадает на миг (см. skill
  `conventions`, раздел про SPA — это нерушимое требование продукта).
- **Ошибки**: доменные ошибки (`ErrValidation`, `ErrNotFound`, `ErrInvalidCredentials`,
  `ErrUnauthenticated`, `ErrForbidden`, …) мапятся в HTTP в одной точке
  (`transport/web/web.go:fail`).
- **Миграции**: схема — версионированные `.sql` в `internal/platform/pg/migrations`.
  Новая таблица = новый файл (следующий номер), не правка старых и не inline-DDL.
- **Аутентификация и роли**: пользователи + роли (гость→user→admin), вход/выход,
  сессии (БД+cookie), восстановление пароля письмом, подтверждение почты (опционально),
  рейт-лимиты. Регистрация по умолчанию закрыта — флаг в настройках (`allow_signup`).
  Защита маршрутов: `requireAuth` / `requireRole`. Личные данные привязываются к
  `OwnerID` (как заметки).
- **Настройки приложения**: типизированный реестр (config + secret) в
  `domain/setting.go`, CRUD под admin (`/admin/settings`).
- **Покрытие**: каждый usecase — unit-тест на фейк-репозитории; транспорт — e2e
  через `httptest` на локальном PostgreSQL (`make pg-up`; без него тесты пропускаются).

## Запуск

```sh
make pg-up          # локальный PostgreSQL в docker
make run            # локально, http://localhost:8080
make test           # все тесты (e2e — против локального PostgreSQL)
make check          # сборка + статанализ + тесты (проверка перед публикацией)
make pg-down        # погасить локальный PostgreSQL
```

Требуется Go ≥ 1.25. Перед тем как считать работу готовой — прогоняется `make check`
(build+vet+test) и приложение поднимается для самопроверки (см. skill `run`).

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ADDR` | `:8080` | адрес прослушивания |
| `DATABASE_URL` | `postgres://postgres:postgres@localhost:5432/app?sslmode=disable` | подключение к базе (в проде платформа подставляет свою) |
| `APP_BASE_URL` | `http://localhost:8080` | базовый URL (ссылки в письмах). В проде платформа подставляет домен приложения |
| `SECURE_COOKIE` | `true` | флаг Secure у cookie сессии (локально по http задавай `false`) |
| `SESSION_COOKIE` | `zv_session` | имя cookie сессии |
| `PLATFORM_API_URL` / `PLATFORM_API_KEY` | — | адрес API платформы и сервис-ключ для отправки писем. **В проде платформа подставляет их сама при деплое.** Без ключа письмо логируется в консоль (грейсфул-фолбэк для локалки) |
| `SETUP_TOKEN` | — | одноразовый код первичной настройки. Пока админа нет, `POST /setup` с этим кодом создаёт первого администратора (email/пароль задаёт человек). **В проде платформа генерирует код при деплое и возвращает его агенту — тот сам заводит админа.** Пустой → `/setup` недоступен |

#### Первый администратор

Создаётся через `POST /setup` (поля `email`, `password`, `token`), пока в системе нет
ни одного админа. После создания первого `/setup` закрывается навсегда. Готового сида
из env-кредов нет — пароль выбирает человек, платформа его не видит.

- **В проде:** платформа генерирует `SETUP_TOKEN` при публикации и возвращает его
  агенту в ответе на деплой; агент сам создаёт первого админа через `/setup`
  (email/пароль называет человек в чате). Токен нигде не хранится.
- **Локально (самопроверка):** задай `SETUP_TOKEN`, затем `curl -d
  'email=...&password=...&token=...' localhost:8080/setup`.

Настройки приложения (через `PUT /admin/settings` под admin-сессией):
- `allow_signup` — открытая регистрация (по умолчанию выключена);
- `require_email_verification` — требовать подтверждение почты (по умолчанию выключено).
  Если включено: после регистрации приходит письмо со ссылкой; до подтверждения вход
  блокируется («подтвердите почту»), есть повторная отправка с ограничением (1/мин, 5/час).
